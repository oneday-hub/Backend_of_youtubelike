# HTTP Headers — Complete Beginner Notes

## 1. What is an HTTP Header?

An **HTTP header** is additional information (metadata) sent along with an HTTP request or response.

Headers help the client and server understand how to handle the communication and its data.

An HTTP message can contain:
- **Method:** What action the client wants to perform.
- **URL:** Which resource the client wants to access.
- **Headers:** Additional information about the request or response.
- **Body:** The actual data being sent, if any.

Example:

```http
POST /api/users HTTP/1.1
Content-Type: application/json
Accept: application/json

{
  "username": "rahul"
}
```

Here:
- `POST` is the HTTP method.
- `/api/users` is the path.
- `Content-Type` tells the server the format of the request body.
- `Accept` tells the server the response format the client prefers.
- The JSON object is the request body.

**Important:** Headers are metadata, while the body usually contains the actual data.

# 2. Most Common HTTP Headers

## 2.1 Accept

**Purpose:** Tells the server which response formats the client can accept.

Example:

```http
Accept: application/json
```

Meaning: The client prefers to receive JSON data.

Common values:
- `application/json` — JSON data
- `text/html` — HTML documents
- `text/plain` — Plain text
- `image/*` — Any image format

**Note:** `Accept` describes the preferred response format, not the request body format.

## 2.2 User-Agent

**Purpose:** Provides information about the software making the request, such as a browser or HTTP client.

Example:

```http
User-Agent: Mozilla/5.0
```

The server may use this information for diagnostics or compatibility decisions.

**Note:** User-Agent information can be modified or spoofed, so it should not be trusted as proof of a user's identity or device.

## 2.3 Authorization

**Purpose:** Carries credentials used to authenticate a request.

Example:

```http
Authorization: Bearer your_access_token
```

In a backend application, a client may send an access token when requesting protected data.

For example, a logged-in VideoTube user might send a token when accessing their profile.

**Note:** Authentication identifies who the user is; authorization determines what the user is allowed to do. Always protect credentials and use HTTPS.

## 2.4 Content-Type

**Purpose:** Tells the receiver the media type or format of the message body.

Example:

```http
Content-Type: application/json
```

Common values:

| Value | Purpose |
|---|---|
| `application/json` | JSON data |
| `text/html` | HTML content |
| `text/plain` | Plain text |
| `multipart/form-data` | Form fields and file uploads |

Example in Express:

```js
app.use(express.json());
```

This middleware parses incoming JSON request bodies so they can be accessed through `req.body`.

**Note for file uploads:** When a browser sends `multipart/form-data`, Multer can parse the uploaded file and form fields. Do not manually set the multipart Content-Type in browser `fetch` requests when using `FormData`; the browser must add the boundary parameter.

## 2.5 Cookie

**Purpose:** Sends cookies that the browser has stored for the relevant website.

Example:

```http
Cookie: sessionId=abc123
```

Cookies can be used to maintain login sessions and remember user preferences.

**Note:** The `Cookie` header is sent by the client. The server typically creates or updates cookies using the `Set-Cookie` response header.

Sensitive cookies should use appropriate attributes such as `HttpOnly`, `Secure`, and `SameSite`.

## 2.6 Cache-Control

**Purpose:** Specifies caching instructions for browsers and intermediary caches.

Example:

```http
Cache-Control: no-store
```

Common directives:

- `no-store` — Do not store the response in a cache.
- `no-cache` — Revalidate before reusing a stored response.
- `max-age=3600` — The response can be considered fresh for 3,600 seconds, subject to other caching rules.
- `public` — The response may be stored by shared caches when otherwise permitted.

**Note:** `no-cache` does not mean "never save." Use `no-store` when the response should not be stored.

# 3. CORS Headers

## What is CORS?

**CORS stands for Cross-Origin Resource Sharing.**

It is a browser security mechanism that controls whether JavaScript running on one origin can access a response from another origin.

An origin consists of the scheme, hostname, and port.

Example:

- Frontend: `http://localhost:5173`
- Backend: `http://localhost:3000`

These are different origins because their ports differ.

## 3.1 Access-Control-Allow-Origin

**Purpose:** Specifies which origin is allowed to access a response through CORS.

Example:

```http
Access-Control-Allow-Origin: http://localhost:5173
```

This allows the specified frontend origin.

**Note:** Avoid using `*` when the application requires credentialed CORS requests.

## 3.2 Access-Control-Allow-Credentials

**Purpose:** Indicates that the browser can expose a CORS response to JavaScript when the request uses credentials, such as cookies.

Example:

```http
Access-Control-Allow-Credentials: true
```

When this is enabled for a credentialed CORS request, the server must specify an explicit allowed origin rather than `*`.

The frontend must also opt in to sending credentials, for example with `fetch`:

```js
fetch("http://localhost:3000/api/profile", {
  credentials: "include"
});
```

## 3.3 Access-Control-Allow-Methods

**Purpose:** Specifies the HTTP methods permitted by the CORS policy for a preflighted request.

Example:

```http
Access-Control-Allow-Methods: GET, POST, PATCH, DELETE
```

**Note:** The correct header name is `Access-Control-Allow-Methods`, with "Methods" plural.

### Important CORS note

`Access-Control-Allow-Origin`, `Access-Control-Allow-Credentials`, and `Access-Control-Allow-Methods` are normally response headers sent by the server.

They do not replace authentication or authorization. CORS is primarily enforced by browsers; it does not stop every non-browser client from making requests.

# 4. Security Headers

## 4.1 Cross-Origin-Embedder-Policy (COEP)

**Purpose:** Controls whether a document can load certain cross-origin resources.

Example:

```http
Cross-Origin-Embedder-Policy: require-corp
```

This can help establish cross-origin isolation when combined with the appropriate other policies and resource permissions.

**Note:** Do not enable it without checking which external images, scripts, and other resources your application needs.

## 4.2 Cross-Origin-Opener-Policy (COOP)

**Purpose:** Controls the relationship between a document and browsing contexts, such as windows or tabs, opened from other origins.

Example:

```http
Cross-Origin-Opener-Policy: same-origin
```

This helps isolate the page from cross-origin documents and can contribute to cross-origin isolation.

## 4.3 Content-Security-Policy (CSP)

**Purpose:** Restricts which sources a browser may load resources from, helping reduce risks such as cross-site scripting (XSS).

Example:

```http
Content-Security-Policy: default-src 'self'
```

This sets the default resource policy to the same origin, unless other directives specify otherwise.

**Note:** A real application may need additional directives for images, styles, scripts, fonts, and API connections. Test the policy before deploying it.

## 4.4 X-XSS-Protection

**Purpose:** An older header intended to control legacy browser cross-site scripting filters.

Example:

```http
X-XSS-Protection: 0
```

**Important:** This header is deprecated and is not recommended as a modern security defense. Prefer a well-designed Content-Security-Policy and safe handling of untrusted input and output.

---

# 5. Request Headers vs. Response Headers

## Request headers

Sent by the client to the server.

Examples:
- `Accept`
- `Authorization`
- `Content-Type`
- `Cookie`
- `User-Agent`

## Response headers

Sent by the server to the client.

Examples:
- `Set-Cookie`
- `Access-Control-Allow-Origin`
- `Access-Control-Allow-Methods`
- `Content-Security-Policy`

Some headers, such as `Content-Type` and `Cache-Control`, can appear in both requests and responses.

# 6. Quick Revision Table

| Header | Main purpose |
|---|---|
| `Accept` | Preferred response format |
| `User-Agent` | Information about the client software |
| `Authorization` | Credentials for authentication |
| `Content-Type` | Format of the message body |
| `Cookie` | Sends stored cookies to the server |
| `Cache-Control` | Caching instructions |
| `Access-Control-Allow-Origin` | Allowed CORS origin |
| `Access-Control-Allow-Credentials` | Permits credentialed CORS responses |
| `Access-Control-Allow-Methods` | Allowed CORS methods |
| `Cross-Origin-Embedder-Policy` | Controls cross-origin embedding |
| `Cross-Origin-Opener-Policy` | Controls cross-origin opener relationships |
| `Content-Security-Policy` | Restricts permitted resource sources |
| `X-XSS-Protection` | Deprecated legacy XSS filter control |

## 7. Final Notes to Remember

1. **HTTP headers are metadata**, not usually the main content of a request or response.
2. `Accept` describes the response format the client prefers.
3. `Content-Type` describes the format of the body being sent.
4. `Authorization` carries credentials; it does not itself decide whether the user has permission.
5. `Cookie` sends stored cookies; `Set-Cookie` is used by the server to set them.
6. CORS controls browser access to cross-origin responses. It is not a replacement for backend security.
7. CSP is a useful modern security header; `X-XSS-Protection` is deprecated.
8. Use HTTPS to protect sensitive information in transit.

1. Review of your loginUser controller
Your authentication flow is correct:
1. Get username/email and password.
2. Find the user in MongoDB.
3. Check whether the user exists.
4. Verify the password using bcrypt.
5. Generate access and refresh tokens.
6. Return the response and set cookies.
However, there are some issues.
Mistake 1: Email or username validation
You wrote:
if(!email || !username){
    throw new ApiError(400, "Email or username is required")
}


This condition requires both email and username.

But your intention is to allow the user to log in using either one.

Correct:
if (!email && !username) {
    throw new ApiError(400, "Email or username is required");
}


Remember:

| Operator | Meaning |
|---|---|
| && | Both conditions must be true |
| || | At least one condition must be true |
Mistake 2: Finding the user
You wrote:
const user = await User.findOne({
    $or: [{ username }, { email }]
});


The idea is correct, but you should avoid putting an undefined field into the query.

A cleaner approach:
const user = await User.findOne(
    email ? { email } : { username }
);


This works because you only need one login identifier.
Mistake 3: Wrong variable in findById()
You wrote:
const loggedInUser = await User.findById(user_id).
select("-password - refreshToken")


There are two problems:
- user_id is not defined in your code. You already have user._id.
- The field selection has an unnecessary space before refreshToken.
Correct:
const loggedInUser = await User.findById(user._id)
    .select("-password -refreshToken");


Mistake 4: Token response and cookies
You wrote:
.cookie("accessToken", accessToken, options)
.cookie("refreshToken", refreshToken, options)


And then:
{
    user: loggedInUser,
    accessToken,
    refreshToken
}


This sends both tokens in cookies and in the response body.

For a cookie-based authentication approach, a better design is:
- Access token: HttpOnly cookie.
- Refresh token: HttpOnly cookie.
- User information: Response body.
You don't need to expose the refresh token in the response body.

Also, secure: true means cookies are intended for HTTPS connections. For local HTTP development, you may need secure: false.

3. Corrected loginUser controller
Here is a cleaned-up version following your intended approach: access token in the response body and refresh token in an HttpOnly cookie.
const loginUser = asyncHandler(async (req, res) => {

    // Step 1: Get login credentials
    const { email, username, password } = req.body;

    // Step 2: Validate input
    if (!email && !username) {
        throw new ApiError(400, "Email or username is required");
    }

    if (!password) {
        throw new ApiError(400, "Password is required");
    }

    // Step 3: Find user using email OR username
    const user = await User.findOne(
        email ? { email } : { username }
    );

    // Step 4: Check whether user exists
    if (!user) {
        throw new ApiError(404, "User not found");
    }

    // Step 5: Verify password
    const isPasswordValid = await user.isPasswordCorrect(password);

    if (!isPasswordValid) {
        throw new ApiError(401, "Invalid password");
    }

    // Step 6: Generate tokens
    const { refreshToken, accessToken } =
        await generateAcessTokenAndRefreshTokens(user._id);

    // Step 7: Fetch user without sensitive fields
    const loggedInUser = await User.findById(user._id)
        .select("-password -refreshToken");

    // Step 8: Cookie options
    const options = {
        httpOnly: true,
        secure: process.env.NODE_ENV === "production"
    };

    // Step 9: Send response
    return res
        .status(200)
        .cookie("refreshToken", refreshToken, options)
        .json(
            new ApiResponse(
                200,
                {
                    user: loggedInUser,
                    accessToken
                },
                "User Logged In Successfully"
            )
        );
});


Important: This version assumes your generateAcessTokenAndRefreshTokens() function saves the refresh token in the user's database document. It also assumes your project uses the same token-generation function you mentioned.
4. Corrected auth.middleware.js
Your middleware has one main responsibility:

Verify the access token and identify the user making the request.
import { ApiError } from "../utils/ApiError.js";
import { asyncHandler } from "../utils/asyncHandler.js";
import jwt from "jsonwebtoken";
import { User } from "../models/user.model.js";

export const verifyJWT = asyncHandler(async (req, res, next) => {

    // Step 1: Get token from cookie or Authorization header
    const authHeader = req.header("Authorization");

    const token = req.cookies?.accessToken ||
        (authHeader?.startsWith("Bearer ")
            ? authHeader.slice(7).trim()
            : undefined);

    // Step 2: Check whether token exists
    if (!token) {
        throw new ApiError(401, "Unauthorized request");
    }

    // Step 3: Verify JWT
    let decodedToken;

    try {
        decodedToken = jwt.verify(
            token,
            process.env.ACCESS_TOKEN_SECRET
        );
    } catch {
        throw new ApiError(401, "Invalid or expired access token");
    }

    // Step 4: Find user using decoded token ID
    const user = await User.findById(decodedToken?._id)
        .select("-password -refreshToken");

    // Step 5: Check whether user exists
    if (!user) {
        throw new ApiError(401, "Invalid access token");
    }

    // Step 6: Attach user to request
    req.user = user;

    // Step 7: Continue to next middleware/controller
    next();
});


Notice something important:

In your login controller, we send the access token in the response body, not in a cookie.

Therefore, your frontend should send it in the Authorization header:
Authorization: Bearer YOUR_ACCESS_TOKEN


If you decide to store the access token in a cookie instead, your original req.cookies?.accessToken approach will work.
5. Important concepts to understand
These are the notes I recommend keeping.
A. What does jwt.verify() do?
const decodedToken = jwt.verify(
    token,
    process.env.ACCESS_TOKEN_SECRET
);


It performs three important checks:
1. Verifies the JWT signature using your secret key.
2. Checks whether the token has expired.
3. Returns the decoded payload if verification succeeds.
For example, if your token was generated with:
jwt.sign(
    { _id: user._id },
    process.env.ACCESS_TOKEN_SECRET,
    { expiresIn: "15m" }
);


The decoded payload will contain the user's _id (and JWT metadata such as iat and exp).
B. What is req.user?
req.user = user;


This is particularly important.

Express allows you to attach custom properties to the request object.

You are attaching the authenticated user's database document to req.user.

Now, subsequent middleware and controllers can access the logged-in user without querying the database again.
C. What does next() do?
next();


next() tells Express:

"This middleware has completed its work. Continue to the next middleware or controller."

For example:
router.get("/profile", verifyJWT, getCurrentUser);


Incoming API request

GET /profile


verifyJWT middleware

Verify access token

Valid
next()


Invalid
Return 401




getCurrentUser controller

Access req.user

7. Notes for your backend notebook
Concept	Purpose
jwt.sign()	Generates a JWT
jwt.verify()	Verifies a JWT
Access token	Provides access to protected APIs
Refresh token	Obtains a new access token
req.cookies	Reads cookies sent by the client
req.header()	Reads request headers
req.user	Stores the authenticated user
next()	Moves to the next middleware/controller
HttpOnly	Prevents frontend JavaScript from reading a cookie
secure	Restricts cookie transmission to secure HTTPS connections

One security note: For production, also configure cookie sameSite appropriately, 
protect cookie-based refresh endpoints against CSRF, and implement refresh-token 
rotation and revocation. Never expose your JWT secret keys.
